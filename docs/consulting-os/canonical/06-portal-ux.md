LEAD EMERGENCE

# 06 — Portal Information Architecture &
UX Specification

Canonical Architecture Specification

Version 1.0 • August 2026

Purpose

Define a clear two-portal experience in which consultants work through the Emergence methodology and clients participate in, understand, and increasingly inhabit the organizational reality the engagement creates.

# 1. UX Thesis

The Emergence Roadmap governs workflow and meaning, but every concept should not become a page. V1 contains two primary experiences: Consultant Portal and Client Portal.

| Portal | Primary user question |
| --- | --- |
| Consultant Portal | What do I need to understand, guide, design, develop, and evaluate across my clients? |
| Client Portal | What do I need to understand, contribute, decide, develop, and do inside our engagement and organization? |

Meridian remains mostly invisible infrastructure underneath both portals.

# 2. UX Principles

## Roadmap as context, not menu explosion

Seven stages remain visible without seven separate top-level modules.

## Attention before density

Home and Overview answer what needs attention rather than showing everything.

## Progressive disclosure

Deep evidence and reasoning are available without overwhelming ordinary users.

## One object, multiple views

The same Goal, Decision, Capability, Meeting, or Outcome can appear in several workspaces without duplication.

## Evidence and meaning remain distinct

Observations, AI suggestions, interpretations, validated insights, and decisions look different.

## Client simplicity

Clients do not need the full consultant diagnostic cockpit.

## New Reality becomes ordinary

Approved consulting outputs become persistent organizational reality rather than a static report.

## Permission-aware UX

UI respects authorization while security remains enforced below it.

## Human authority is visible

AI suggestions look suggested; validated conclusions show reviewer/authority.

## History without clutter

Current state is default; historical versions are accessible when needed.

# 3. Global Product Shell

| Element | Behavior |
| --- | --- |
| Portal switch | Only for users entitled to both contexts. |
| Organization context | Always visible inside client work. |

A consultant should never be uncertain which organization's data is open.

# 4. Roadmap UI

SEE REALITY → REFRAME REALITY → ALIGN WITH REALITY → BUILD CAPABILITY → PRODUCE VALUE → NEW REALITY → SEE AGAIN

- Show compact stage status and current focus.

- Clicking a stage changes lens or opens the relevant workspace/artifact; it does not require one page per stage.

- Objects may carry a small stage badge showing where they entered the reasoning chain.

- Stage 6 is always NEW REALITY; Live in Your Organization is the explanatory posture.

- SEE AGAIN visually loops toward SEE REALITY.

# 10. Discovery — SEE REALITY

| Tab | Purpose |
| --- | --- |
| Portrait | History, mission, structure, stakeholders, strategy, systems. |
| Assessments | Emergence 360 and future instruments. |
| Interviews | Plan, conduct, transcribe, review stakeholder interviews. |
| Evidence | Documents, metrics, workflows, source material. |
| Observations | Source-grounded observations. |
| Patterns | Suggested/accepted patterns with support and contrary evidence. |

- Portrait separates stated organizational claims from observed reality.

- Assessment results are not labeled diagnosis.

- Evidence detail shows source location and downstream claims it supports/challenges.

- Uploading evidence does not automatically create a Pattern or Insight.

- Pattern detail shows support, contrary evidence, scope, recurrence, origin, and review state.

Evidence → Observation → Suggested Pattern → Consultant Review

## 11.1 Assumption Register

| Field | Purpose |
| --- | --- |
| Assumption | What are we treating as true? |
| Status | Untested/Supported/Challenged/Disproven/Superseded. |
| Evidence For/Against | Make testing visible. |
| Influences | Show decisions/designs depending on it. |
| Review Trigger | When to test again. |
| History | How status/confidence changed. |

## 11.2 Reframing

What are we seeing? → What might it mean? → What alternatives exist? → What best explains it? → What possibility does it reveal?

AI suggestions remain visually distinct from human-validated Insight or Diagnosis.

## 11.3 Future

Use the canonical narrative: What Was True → What Changed → What Is True Now → What That Means → What Must Become True Next → What Could Become Possible.

## 11.4 Alignment

Purpose → Responsibility → Authority → Boundaries → Interfaces → Support → Accountability → Success Measures

Alignment Conflicts are reviewable suggestions, never automatic declarations.

## 12.1 Coaching

Coaching follows the interaction pattern of the ministry meeting concept: recurring relationship, preparation, agenda, history, shared/private notes, commitments, follow-up, and development progress.

| Section | Function |
| --- | --- |
| Relationship | Participant, coach, purpose, development focus. |
| Before We Meet | Prep, previous commitments, permitted Meridian context. |
| Agenda | Editable shared agenda. |
| Conversation | Shared notes with clearly separated private controls. |
| Commitments | Owner, action, due/review date. |
| Development | Capabilities/goals connected to coaching. |
| History | Prior sessions and progress. |

Private coaching information is never silently promoted into organizational intelligence.

# 23. Consultant vs. Client Visibility by Workspace

| Domain | Consultant experience | Client experience |
| --- | --- | --- |
| Raw Evidence | Broad within assignment/visibility. | Only explicitly shared/authorized evidence. |
| Observations | Create/review full permitted set. | Participate/view when shared. |
| AI Suggestions | Review and validate. | Normally hidden until intentionally shared; if shown, clearly labeled. |
| Assumptions | Full register. | Shared assumptions appropriate to engagement/leadership role. |
| Diagnosis/Insight | Full reasoning and review. | Approved client-visible conclusions. |
| Coaching | According to relationship/privacy. | Own coaching-shared content only. |
| Decisions | Create/link/trace reasoning. | Approved decisions relevant to user. |
| Outcomes | Full consulting evaluation. | Curated appropriate progress/outcomes. |
| Signals | Descriptive consultant review. | Only intentionally shared signals/trends. |

# 24. Record Detail Pattern

Major domain objects should use a consistent detail-page pattern so users learn one interaction model.

| Area | Contents |
| --- | --- |
| Header | Title, type, status, roadmap stage, owner, visibility. |
| Summary | Current canonical statement/meaning. |
| Evidence/Reasoning | Sources and upstream relationships. |
| Relationships | What this object supports, challenges, informs, requires, measures, etc. |
| Review | AI/human origin, validation state, reviewer, confidence/limitations. |
| Activity | Comments/actions where appropriate. |
| History | Versions, status changes, superseded records. |
| Actions | Context-appropriate edit, review, validate, supersede, link, archive. |

# 25. AI Interaction Pattern

Avoid a generic AI chat box as the primary interaction model. AI should appear where it can assist a defined consulting task.

| Context | AI action |
| --- | --- |
| Evidence | Extract candidate observations. |
| Patterns | Suggest clusters/patterns and contrary evidence. |
| Assumptions | Suggest assumptions to test, never auto-validate. |
| Reframe | Offer alternative interpretations. |
| Alignment | Surface possible conflicts. |
| Meeting Prep | Summarize permitted changes and open commitments. |
| Outcomes | Compare hypothesis, measures, and observed results. |
| Signals | Surface descriptive changes/questions, not autonomous diagnosis. |

Every substantive AI result exposes origin, review state, and source path consistent with Document 04.

# 26. Empty, Loading, and Error States

- Empty states explain what belongs here and the next useful action.

- Do not fabricate example client findings in production empty states that could be mistaken for real data.

- Loading states should not imply AI is diagnosing the organization.

- Permission-denied states do not reveal inaccessible record details.

- Missing evidence or insufficient data is communicated plainly.

- Failed AI generation never replaces existing validated content with a fallback presented as truth.

# 27. Notifications and Attention

| Type | Example |
| --- | --- |
| Assignment | Assessment, action, development resource. |
| Review | AI suggestion or interpretation awaiting consultant review. |
| Meeting | Prep due, agenda updated, commitment follow-up. |
| Decision | Approval/reconsideration requested. |
| Assumption | Review trigger/date reached. |
| Outcome | Measurement/outcome review due. |
| Security | Membership/visibility change where user notification is appropriate. |

Notifications should drive action, not become a second dashboard.

# 28. Mobile and Responsive Priorities

- Client Home, Meetings, assessment participation, commitments, and coaching prep should work well on mobile.

- Consultant deep analysis, Reality Map, Alignment Architecture, and evidence synthesis may prioritize desktop while remaining readable responsively.

- Do not compress complex relationship graphs into unusable mobile diagrams; provide list/card alternatives.

- Critical actions and privacy labels remain visible at small sizes.

# 29. Accessibility and Comprehension

- Use semantic headings, keyboard-accessible controls, visible focus, and accessible form labels.

- Do not communicate epistemic state or security scope by color alone.

- Prefer plain organizational language over internal database terminology in client-facing UI.

- Provide tooltips/help for specialized concepts such as Assumption, Pattern, Future-State Principle, Capability, Harvest & Soil.

- Keep stage labels and canonical terminology consistent across the product.

# 31. V1 UX Non-Goals

- No full HRIS.

- No project-management replacement.

- No generic task-management suite.

- No autonomous organizational diagnosis.

- No mature Pulse/drift dashboard before longitudinal evidence exists.

- No cross-client benchmarking.

- No separate seven-module application shell.

- No client exposure to every raw consultant note or AI suggestion.

- No generic chatbot as the product's central interface.

# 32. End-to-End Consultant Journey

Home → Client → Overview → Discovery → Reality Map → Reframe/Assumptions → Future → Alignment → Development → Outcomes → New Reality/Baseline → Signals/See Again

The consultant can move backward at any point because new evidence may challenge prior reasoning.

# 33. End-to-End Client Journey

Home → Participate → Understand Our Organization → Prepare/Meet → Develop → Act on Commitments → See Progress → Inhabit New Reality

The client journey should feel increasingly less like 'being consulted' and more like living inside a clearer organization.

# 34. UX Acceptance Criteria

1. A consultant can identify the current organization and engagement at all times.

1. A new consultant can locate evidence, assumptions, decisions, capability work, outcomes, and meetings without learning seven separate modules.

1. A client member can find what requires their attention from Home.

1. AI suggestions are visually distinguishable from validated conclusions.

1. A user can move from a major Insight or Decision back to supporting evidence when authorized.

1. Private coaching notes cannot be mistaken for shared notes.

1. Current identity/design is the default while historical versions remain accessible.

1. NEW REALITY uses the canonical stage name everywhere.

1. Signals does not claim mature drift detection in V1.

1. The same Meeting/Decision/Goal/Capability object is reused across views rather than duplicated.

1. Permission-denied UI does not reveal inaccessible content.

1. Client Progress communicates transformation without exposing raw consultant analysis.

1. Mobile client flows support meeting prep, assessments, commitments, and coaching.

1. Empty states teach the next action without inventing organizational facts.

# 35. Implementation Hand-off

- Build the global shell and context model first.

- Implement Consultant Home/Clients and Client Workspace routing.

- Build Discovery on top of Document 03 domain entities, not ad hoc page-specific tables.

- Build Strategy using shared Assumption, Future State, Decision, and Alignment objects.

- Build the shared Meeting engine before separate meeting implementations proliferate.

- Reuse the meeting interaction pattern for Coaching with stricter privacy scopes.

- Build Client Portal as permissioned views/actions over the same domain objects.

- Keep Signals descriptive until the later Pulse phase.

- Run UX acceptance criteria alongside Document 05 security tests.

# 36. Definition of UX Integrity

Lead Emergence has UX integrity when the interface makes the consulting method easier to practice without forcing users to think like database architects or turning the roadmap into navigation clutter.

Consultants experience the roadmap. Clients experience the organization the roadmap is helping create. Meridian preserves why. The interface shows what each person needs to do next.
